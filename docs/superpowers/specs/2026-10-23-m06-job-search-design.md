# M06 Job Search — Design

Date: 2026-10-23. Requirement: `R-M06-JOBS`; milestone: `docs/milestones/M06-job-search.md`.

## Intent

Give MCP clients structured job discovery, honest freshness signals, explicit provider attribution, bounded detail lookup and optional local saved jobs/searches. A job result must never imply that a position is newly posted, still open, eligible for remote work in a specific country, or offers visa sponsorship without evidence.

## Access and provider truth

Ordinary LinkedIn OAuth identity and member publishing scopes do not grant general LinkedIn Jobs or Talent Solutions search. Talent APIs are partner/contract dependent. M06 will not impersonate Talent API access, scrape restricted pages, bypass challenges, or enable automated applications. Global search requires a separately configured legitimate `EXTERNAL_DISCOVERY` provider or authorized `PARTNER_API` adapter, with documented access conditions. There is **no bundled search provider**. No source yields explicit `unavailable`, never `available` with a fictitious empty list. Provider credentials, actor identities and base URLs are trusted host configuration only and are never MCP tool parameters.

## Data contracts and source evidence

`JobSearchQuery` is a strict object with required `keywords` (trimmed, 1–120 characters), optional `location` (1–120), `workplace` (`remote|hybrid|on_site`), `employmentType` (`full_time|part_time|contract|temporary|internship`), `postedSince` (strict UTC instant), `limit` (1–50, default 10), and `sort` (`recent|relevance`, default `recent`). Empty/unknown or simultaneous provider selection, token, endpoint, untrusted URL, or actor override fields fail locally before any provider call. A user-supplied location is a filter/search hint, never proof of eligibility to work there.

`NormalizedJob` includes a stable source-scoped `id`, `title`, `companyName`, and a trusted `source` of `{id,name,provider,retrievedAt}` with optional verified evidence URL. Optional `description`, `location`, `workplace`, `employmentType`, `canonicalUrl`, and salary range/currency/period are supplied only where present in actual provider evidence. `confidence` (0–1) is absent unless separately evidenced in trusted adapter context; raw listing scores cannot set it. There are no salary filters in M06: differing currencies, gross/net conventions and pay periods cannot be compared or converted without verified evidence. Strings are bounded and treated as plain untrusted text. No inferred company identity, date, salary, sponsorship, employment terms, or country eligibility. Job description text is untrusted data, never tool instructions. Raw `visaSponsor:true` and `remoteWorldwide:true` claims cannot become derived eligibility or sponsorship classifications; CV matching, requirements extraction, sponsorship scoring and applications remain outside M06 (see M07).

Job links must be absolute HTTPS public destinations without embedded credentials, fragments, nonstandard ports or local/private hosts (including normalized IPv4, IPv6, link-local and loopback ranges). The pure normalizer never fetches a link or follows redirects. The originating adapter must be entitled to return a link. A plausible URL alone does not prove an official LinkedIn job identity. Deduplication is restricted to trusted same-provider job IDs until independent identity evidence establishes cross-provider equivalence; titles, company names and prose are insufficient.

The core validator blocks syntactically private addresses, common credential query parameters and known dynamic-IP wildcard domains (`nip.io`, `sslip.io`, `localtest.me`), but cannot establish DNS resolution trust. **Any future provider adapter that actually fetches a URL must independently resolve A/AAAA records and reject private, metadata, loopback and link-local addresses at every connection and redirect, including rebinding**. Source URLs are output data, never approved internal HTTP fetch targets.

Date evidence uses a **discriminated per-job** `PostingDateEvidence` contract:

- `{state:'unknown'}`: no `postedAt` at all. Missing or malformed claims cannot be silently replaced with the time of retrieval.
- `{state:'reported',postedAt:UTC,sourceClaim:'provider_reported'}`: parseable date present in the raw listing but not independently confirmed. The raw item's `verified:true`, `checkedAt`, `updatedAt`, recruiter comment or purported evidence link cannot elevate it.
- `{state:'verified',postedAt:UTC,verifiedBy:string,method:'direct_employer_listing'|'official_posting_api'|'trusted_independent_audit',evidenceUrl:HTTPS,checkedAt:UTC}`: only a **trusted host-owned per-record** `TrustedJobContext.verifiedPostingDate` object can supply this. The attestation includes its exact `providerId`, `jobId`, checked timestamp, and (where present) `canonicalUrl` identity binding. The trusted verifier records an independently checked listing and its canonical evidence locator. Raw provider result fields cannot create or override this attestation. The normalized record validates all fields and requires the attestation's provider/job identity to equal the source-scoped normalized job identity, with UTC calendar validity, `postedAt <= checkedAt <= retrievedAt`, and matching normalized canonical URL when attested. Conflicting raw/verified posting timestamps fail closed. If no independent verifier is configured, the verified state is impossible and results remain `reported` or `unknown`.

The local `retrievedAt` proves only when data was fetched, not when a job was posted. `updatedAt`, `firstSeenAt`, and listing modification times are never silently substituted for posting dates. Filters on `postedSince` must never treat `reported`/`unknown` as verified recency or return a misleading complete-empty result; report uncertainty/partial coverage instead. Saving a listing locally never upgrades its date evidence.

### Exact freshness and completeness policy

The provider coverage attestation also declares `honoredSort: 'recent'|'relevance'|null`. A provider may claim a sort was honored only when it can prove source ordering or the local router can deterministically establish the requested ordering from independently evidenced timestamps. `sort:'relevance'` preserves stable source order without fabricating a cross-provider relevance score. Neither the local filter nor a provider's returned item count can prove exhausted source coverage. Repeated source-scoped job IDs are grouped after non-date eligibility, and independently verified evidence outranks reported/unknown evidence before the date cutoff; contradictory verified posting dates force incomplete coverage, never first-match success.

Each trusted `JobProvider.search` returns `{ jobs, coverage }`, where `coverage` contains `complete: boolean`, `honoredFilters: readonly ('keywords'|'location'|'workplace'|'employmentType'|'postedSince')[]`, `hasMore: boolean`, and `verifiedDateCoverage: boolean`. The adapter sets `complete:true` **only** when it exhaustively covered the requested source results and all stated filters for that exact query; a capped first page or unknown next cursor is `complete:false`. `honoredFilters` reflects criteria actually applied at source or exhaustively checked across all fetched pages, not raw response claims. `verifiedDateCoverage:true` additionally requires independent verification of the relevant posting-date range for every candidate, even if zero results are returned (e.g. authenticated provider date-filter proof). These fields are trusted adapter statements that the service validates and checks against the query; an untrusted raw API payload cannot set them.

`JobSearchResult` includes typed `freshnessCoverage: { state:'verified'|'incomplete'; unknownDateCount:number; reportedDateCount:number; omittedUncertainCount:number; providerCoverage: ... }`. For `postedSince`, only posting dates with `state:'verified'` may prove eligibility. Verified posts older than the inclusive UTC bound are excluded. Reported/unknown candidates are omitted from _verified matches_ but counted as uncertain, which forces `partial` even if zero jobs remain; the missing provider date filter proof also forces `partial`. For `sort:'recent'`, order verified dates descending, then reported dates (clearly labeled) descending within their own group, then unknown dates last; never use retrieval/firstSeen/updated timestamps as posting recency. If a requested filter is not honored or a provider has more pages, return `partial`, even when other providers succeeded or returned zero jobs. `available, jobs:[]` requires at least one legitimately configured, consulted, successful provider and complete, exhaustive coverage of the entire requested query, including verified freshness when required. Provider timeout/permission/rate issues remain typed errors; any partial success is still partial. Local truncation at result limit must not imply complete discovery of all jobs.

## Routing, persistence, and MCP

Use a bounded read-only job discovery service with trusted immutable provider metadata (`providerId`, `providerType`, `name`, `supportsSearch`, `supportsDetails`), max three providers, per-provider timeouts/body/item caps, typed outcomes `success|unavailable|permission_required|rate_limited|failed`, and sanitized error messages. `JobSearchQuery` has no `kind`; do not carry M05's `supportedKinds` property into this contract. Preserve every eligible provider outcome. Successful empty only means a consulted source actually completed an exhaustive query; any mixed success/failure or unverifiable freshness is partial. No fallback provider changes attribution.

Shared stdio/HTTP runtime registers strict `linkedin.jobs.search` and `linkedin.jobs.get` (when a provider supports details), with local tool status mapped from domain `available|partial|unavailable|permission_required|rate_limited|failed`. A missing provider is non-success `unsupported`. A configured legitimate provider gets its own per-result provenance; the outer MCP aggregator stays `LOCAL_ONLY`. Search inputs cannot choose providers, inject secrets or override an API target. A details request uses strictly validated `JobRef: {sourceId,jobId}`. `sourceId` refers **only** to a trusted configured provider's immutable ID (a lookup identity, not an arbitrary provider endpoint or capability escalation); `jobId` is the bounded stable source-scoped posting ID. The router resolves this exact pair to an allowlisted provider with `supportsDetails:true`, and rejects unknown/mismatched identities before any network. `getDetails(jobId,signal)` is optional provider behavior; unsupported detail is `unavailable` without a request. Validate that the returned normalized job ID/source exactly match the requested ref and that details cannot add unverified date evidence or a spoofed canonical URL. Never fetch a caller-supplied URL/host. Bound detail body size and timeout like search; reject redirects or unexpected response identity in adapters.

Saved searches/jobs are explicit **local** mutations in an opt-in persistence store, scoped to **one trusted OS user/workspace** in a local stdio deployment. The sole storage path is host configuration (e.g. `LINKEDIN_MCP_JOB_SAVED_PATH`); disabled by default. This is a local workspace across that OS user's chosen LinkedIn accounts, not a LinkedIn-account bookmark or application, and not an authenticated multi-tenant store. The HTTP server currently validates loopback Host/Origin but has **no authenticated MCP caller identity** and shares a runtime across clients: **never expose any saved-state read/write through HTTP** in M06. All saved-state MCP entrypoints on HTTP return a non-success unavailable/permission-required result and cannot open the store, even if a local path is configured. Do not derive an owner from an MCP argument, a global OIDC subject or unauthenticated headers. Future multi-user HTTP storage requires separately designed per-request authenticated workspace identity (M16), not a default fallback.

For local stdio opt-in, use bounded schemas and counts (at most 500 saved jobs, 50 saved searches, 2 MiB store bytes), stable source-scoped idempotent keys, explicit list/get/save/remove, private store file mode `0600` and directory `0700`, validated path/parent without symlink traversal, safe OS-user ownership, atomic write-to-temp + fsync/rename + persisted readback, and advisory or equivalent cross-process serialization. Corrupt data, unsafe permissions, concurrent uncertainty and persistence failures must fail closed and never silently overwrite/reinitialize existing records. Removing saved state deletes only that local record; no LinkedIn remote delete/revocation is implied. Saved records have no OAuth token, recruiter contact secrets, application submission, or network mutation. Fit scoring, qualification extraction and visa signal analysis belong to M07.

## Acceptance and verification

- RED→GREEN tests for strict query modes, strings, UTC date parsing, untrusted URLs/hosts, missing vs reported vs verified freshness, no fabricated fields, trust-derived source metadata and deterministic duplicate handling.
- Provider tests cover default unavailability, configured empty, mixed partial, permission/rate/failure taxonomy, hostile payloads, timeout, body bounds and result provenance; no official Talent access inferred.
- Completeness tests cover reported-only/unknown dates with `postedSince`, zero results without exhaustion proof, provider `hasMore`, filters not honored, verified fresh/old dates and ordering of mixed verified/reported/unknown evidence; never claim complete empty from a partial page.
- Details tests cover two providers with identical `jobId`, source-scoped `JobRef`, unsupported provider, unrecognized/forged source, wrong response ID, oversized response and raw provider claims of verification; no caller URL fetch.
- Real stdio/HTTP MCP tests prove tool registration, default unavailability, exact input validation, client-specific errors, configured provider attribution and no credentials in output.
- Local saved-job tests prove read-back durability and safe recovery from interrupted writes without relying on external job applications.
- Independent security/provenance review, zero unresolved Critical/Important findings, exact-final-head CI green, squash merge, and post-merge `main` verification before M07.

## Owner-authorized engineering rulings

Use existing TypeScript core/server architecture and M05 patterns. Build independent job schema/freshness logic because job posting dates, saved state and work eligibility have different semantics. Source availability is determined by verified configuration, never by a network scrape or fabricated Talent capability. Routine design and implementation choices are pre-authorized under `AGENTS.md`.

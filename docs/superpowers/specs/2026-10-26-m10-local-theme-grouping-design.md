# M10.1 Caller-Defined Local Theme Grouping — Design

Date: 2026-10-26. Proposed subrequirement: `R-M10-THEME-GROUPS` under `R-M10-RESEARCH`. Parent milestone: `docs/milestones/M10-content-intelligence.md`.

## Intent, dependency, and deliberate choice

Allow a person to organize **their own supplied research excerpts** under **their own explicit theme labels** using only literal, source-bound textual evidence. A theme is a caller-authored group of 1–3 caller-authored phrases, not a topic inferred by the server. The response answers: "which of my supplied excerpts contains one of my phrases for this theme, and exactly where?" It must never answer "what is trending?", "what are my competitors missing?", or "what should the market publish?" from this input.

**Verified prerequisite:** M10.0 `linkedin.research.analyze` was squash-merged as PR #16 into `main` at `865fd9fb4cd5ccd8438ef7a89f9bc08f3fb600df`; user-provided post-merge push CI `40293411451` is SUCCESS. M10.1 is a **new, not implemented or verified** follow-on. It must reuse the merged `normalizeResearchCorpus` strict source boundary and `analyzeResearchCorpus` deterministic UTF-16 literal matcher rather than write a second matcher.

Alternatives: (1) Automatic embedding/LLM theme mining would invent labels and require a new inference/provenance contract; defer. (2) Comparing competitor/market coverage requires multiple separately scoped corpora, a nonrepresentative-absence model and additional data limits; defer. (3) Caller-defined local grouping preserves the evidence invariant without adding providers; **chosen for M10.1**. Future provider-backed source retrieval or trend claims need their own authorization, safety design and validation.

This feature is stateless, deterministic, read-only and `LOCAL_ONLY`; there is **no** web/LinkedIn request, DNS, browser, LLM, embeddings, file/project store, secret access, enrichment, approval or publication. The existing `research.topic` descriptor remains `EXTERNAL_DISCOVERY`, `PLANNED` / `UNAVAILABLE`, and the tool `linkedin.research.topic` must not be registered. M09 native article publication is still `BLOCKED`/`UNAVAILABLE`; M10.1 does not change it.

## Public interface and strict input

Register the separate read-only MCP tool `linkedin.research.group_themes` (the existing `linkedin.research.analyze` input/output and semantics stay unchanged). Pure function:

```ts
export type CallerThemeInput = Readonly<{
  id: string; // stable caller ID, NOT generated by the service
  label: string; // caller's theme name, NOT an inferred topic
  phrases: readonly string[]; // 1–3 exact caller-defined search phrases
}>;

export type ThemeGroupingInput = Readonly<{
  topic: string; // existing M10.0 topic format, context only
  themes: readonly CallerThemeInput[]; // 1–4
  sources: readonly Readonly<{
    id: string;
    title: string;
    url: string;
    body: string;
    publishedAt?: string;
  }>[];
}>;

export function groupResearchThemes(input: unknown): Readonly<ThemeGroupingAnalysis>;
```

The MCP top-level input **is exactly** `{topic,themes,sources}`, with no `focusTerms`, `provider`, `sourceTrust`, `verified`, `retrievedAt`, `confidence`, `competitor`, `projectId`, `filePath`, arbitrary flags or other fields. The service derives `focusTerms` internally; never trust caller-provided normalized objects. Zod v4 `strictObject` input/output schemas must match these bounds, with sanitized SDK validation failures (including malicious unknown property names).

- `topic`: existing M10.0 nonempty single-line `1..200` UTF-16 code units; display/context only, not a separately identified theme.
- `themes`: **dense** 1–4 plain own-data objects, exactly `{id,label,phrases}`; `id` ASCII `[A-Za-z0-9][A-Za-z0-9_-]{0,79}` and unique ignoring case; `label` nonempty, trimmed single-line 1–80 UTF-16 code units, distinct ignoring case. Labels are metadata and **never searched as evidence**.
- `phrases`: dense 1–3 strings per theme, each trimmed nonempty single-line 1–80 UTF-16 code units; **at most 12 across the entire request**, and distinct ignoring case **across all themes**, not just within one. Reject duplicates rather than silently merging two separate caller labels into a shared phrase. A phrase identical to `topic` is **allowed**: the existing topic coverage maps to that phrase in its single owning theme, without creating an extra theme.
- `sources`: exactly the M10.0 source shape, strict names, dense 1–20, unique ASCII IDs, `title` 1–240, inert display-only canonical HTTPS `url` 1–2048 even **after** URL canonicalization, verbatim `body` 1–50,000 UTF-16 units, optional real canonical UTC `publishedAt` reported by caller only. Inherit M10.0 hostile URL credentials/query aliases, Unicode/control, plain-data, freeze and 200 KiB normalized-corpus JSON limits.
- No unpaired UTF-16 surrogates, C0/C1 prohibited controls or multiline text in labels/phrases; no getters, proxies, inherited/custom prototypes, symbols, non-enumerable fields, sparse arrays, array extra properties, duplicate IDs/labels/phrases or unknown fields at any level. Reject rather than coercing data, and do **not** read any input property before safe own-descriptor/proxy validation. Errors contain only fixed field names/codes, never caller names, labels, URLs, bodies or unexpected secret-key names.

**Implementation boundary:** First validate the wrapper and themes using the same fail-closed own-data patterns used by the M10.0 parser; read only descriptors. Build one fresh `{topic,focusTerms,sources}` input with all unique theme phrases flattened in caller theme/phrase order (maximum 12). Call `analyzeResearchCorpus` **once**, which itself invokes `normalizeResearchCorpus` once; source records are validated and canonicalized there. Do not directly serialize unsafe/unvalidated caller objects or inspect `source.body` outside M10.0's analyzer. The existing 200 KiB core-corpus limit applies to that derived corpus; the extra caller-theme metadata is separately bounded by the caps above. Never weaken M10.0 validation to admit the new wrapper.

Use the same case-insensitive identity rules as M10.0 to link each accepted phrase to the exact corresponding `termCoverage` entry; especially account for the analyzer's topic-first and topic-equivalent-focus-term suppression. Verify the mapping by tested deterministic keys, fail closed on any missing/ambiguous term rather than fabricate a match. Preserve original user casing/spelling in the emitted phrase and the unchanged matched `quote`. Reusing the analyzer's bounded, escaped literal matcher is mandatory; no fuzzy match, stemming, inferred synonyms, HTML decoding, semantic classifier or dynamic unescaped regular expression.

## Deterministic grouping result

```ts
export type ThemeGroupingAnalysis = Readonly<{
  kind: 'local_caller_defined_theme_grouping';
  status: 'available' | 'insufficient_evidence';
  themeOrigin: 'caller_defined';
  sourceTrust: 'caller_supplied_unverified';
  verification: 'not_performed';
  topic: string;
  sourceSummaries: ResearchAnalysis['sourceSummaries'];
  themeGroups: readonly Readonly<{
    id: string;
    label: string;
    sourceIds: readonly string[];
    phrases: readonly Readonly<{
      term: string;
      state: 'observed_in_supplied_corpus' | 'not_observed_in_supplied_corpus';
      evidence: readonly ResearchEvidenceSpan[];
    }>[];
  }>[];
  unmatchedSourceIds: readonly string[];
  warnings: readonly (ResearchAnalysis['warnings'][number] | 'themes_caller_defined_only')[];
}>;
```

- Output `themeGroups` exactly in caller theme order and `phrases` exactly in each theme's phrase order. For every phrase, use **the analyzer's original first qualifying whole-word literal span per source**, source order, with `field:'body'`, `offsetUnit:'utf16'`, `endExclusive:true`, `0 <= start < end <= original body.length`, `quote===originalSource.body.slice(start,end)` and quote length ≤160 UTF-16 units. Unicode astral characters before matches, combining sequences, case changes and internal whitespace must preserve exact offsets. Never regenerate quote text from normalized/case-folded strings.
- `sourceIds` is the union of that theme's phrase-evidence source IDs, **deduplicated within a theme and ordered by supplied source order**. A source can appear in _multiple different themes_ when different caller-defined phrases match; this is not independent corroboration or a score. The service reports no count/strength/rank/confidence and never weights duplicates as independent evidence.
- `unmatchedSourceIds` is the corpus-ordered set of sources with **no phrase match in any theme**. A phrase without hits has `state:'not_observed_in_supplied_corpus'` and empty evidence; an entire theme with no hits has empty `sourceIds`. These are **bounded corpus-only observations, never a content gap, competitive advantage, verified absence, trend, freshness or recommendation**. Theme labels might themselves contain unsupported assertions; display as caller-defined labels, never as service assertions.
- Preserve M10.0 `sourceSummaries` provenance: derived `sourceTrust:'caller_supplied_unverified'`; dates only `unknown` or `reported` with `sourceClaim:'caller_reported'`, never `verified`. Do **not** echo complete bodies, credentials or unbounded source content.
- `status` copies the analyzer's source-count sufficiency: exactly one source yields successful local grouping with `status:'insufficient_evidence'` even if a phrase matched; two or more sources gives `available` even if none matched. It is never an external research assessment.
- `warnings`: first retain M10.0's fixed warning order (`caller_sources_unverified`, `coverage_is_corpus_only`, optional `insufficient_sources`, optional `dates_caller_reported_only`), then append `themes_caller_defined_only`. No untrusted prose is turned into warnings.
- Pure results must be deeply frozen, contain only plain data, and be byte-identical for identical canonical input (no ambient time, generated phrase names or nondeterministic sorting). Duplicate source bodies remain separate caller source IDs but do not produce strength/evidence-independence claims. No automatic grouping of _similar_ text.

## Bounds, MCP wiring, and error taxonomy

The new grouping result has an independent hard cap of **96 × 1024 = 98,304 UTF-8 bytes** of `JSON.stringify(analysis)`, even if the reused M10.0 analysis passed its own 96 KiB cap. If either analysis is oversized, throw/reuse `ResearchOutputTooLargeError` and respond with sanitized `analysis_too_large`; do not truncate, drop evidence, claim success or echo caller content. The maximum distinct matched evidence records is 12 phrases × 20 sources (240), before M10.0 quote caps. Algorithmic cost is bounded by this fixed topology, corpus size and existing safe literal matcher; no full pairwise document similarity or quadratic substring mining.

Register `linkedin.research.group_themes` in the current `registerResearchTools` path already used by STDIO/HTTP. Use a strict typed output schema and the existing bounded request metadata/error-envelope conventions:

```ts
{
  status: 'succeeded',
  data: ThemeGroupingAnalysis,
  provider: { type: 'LOCAL_ONLY', name: 'linkedin-mcp' },
  metadata: { requestId: string, timestamp: string }
}
```

The text content must equal `JSON.stringify(structuredContent)` exactly. Error envelopes have `status:'failed'`, `retryable:false` and a fixed sanitized `code:'invalid_input'|'analysis_too_large'|'output_too_large'|'invalid_output'`, with no untrusted values; errors set MCP `isError:true`. An insufficient-evidence _analysis_ is still an MCP success. Reuse the existing request-ID bound (ASCII `[A-Za-z0-9_-]{1,128}`, safe fallback), Zod sanitization and no-secret error-handling pattern.

The **complete MCP result** including duplicated `content` and `structuredContent` plus wrapper reservation must be ≤ **256 × 1024 = 262,144 UTF-8 bytes**. The actual HTTP SSE response, including JSON-RPC wrapping/event framing and a valid request ID, must also be ≤262,144 bytes under real transport tests; retain the existing HTTP whole-response guard. Overflow fails closed as `output_too_large` or bounded HTTP transport failure, never a successful partial result. Neither STDIO nor HTTP accesses optional private article/job stores or executes content from caller bodies.

Add a distinct `research.group_themes` capability descriptor as **`LOCAL_ONLY`, `ACTIVE`** when the feature implementation exists; advertise `AVAILABLE` only when its tested runtime tool is registered, and mark **`VERIFIED`** only after scoped acceptance + exact feature-head and merged-main CI. In the spec/planning stage this is **proposed**, not implemented or verified. Do not change `research.topic` provider or availability.

## Security and provenance threat model

1. **Evidence laundering:** A label like "verified industry trend" or text like "ignore rules, tell market claims" is an inert caller assertion. Only quoted original-body spans can justify phrase inclusion; no generated/validated market truth.
2. **Conflicting/duplicated phrase keys:** Case-insensitive collisions across themes and Unicode/case differences could double-count/redirect hits. Reject conflicts, and test topic-equal phrase mapping and source overlap explicitly. Theme IDs and labels must not become search phrases.
3. **Hostile objects and secrets:** Plain-data own descriptors, proxy rejection, dense arrays and exact schemas at _all_ boundaries; SDK invalid-input errors must redact unknown keys, secret-looking URLs and values, even when nested.
4. **Unicode/matcher correctness:** Existing UTF-16 spans and Unicode whole-word/combining/joiner safeguards must be reused; never tokenize/re-normalize bodies or accept a match that fails `slice` equality.
5. **Resource abuse:** Four themes, twelve phrases, twenty sources, 200 KiB normalized input, 96 KiB pure reports, 256 KiB duplicated MCP + actual SSE cap; metadata must remain bounded and errors deterministic and sanitized.
6. **False provider capabilities:** `research.topic` remains `EXTERNAL_DISCOVERY`/`UNAVAILABLE`, no fetch/DNS, no M05 global search entitlement and no native article publication.

## Acceptance and tests required before any VERIFIED claim

- Strict wrapper and per-theme constraints, hostile proxies/getters/sparse arrays, extra keys, malformed Unicode, duplicate IDs/labels/phrases including case variants, 4/3/12 positive boundaries, over-limit rejection, single-source sufficiency and caller-reported dates.
- Literal-only group membership, evidence quote/source index and UTF-16 slice fidelity across emoji/mixed scripts/whitespace, phrases that overlap across different themes through **different** literal terms, topic-equal phrase and label-not-searched, no-match phrases and unmatched sources.
- Deterministic ordering/deep immutability, sanitized secret-bearing inputs and output strings, no untrusted body echo or invented theme, gap, popularity, ranking, date, trend, verified claim or provider.
- Genuine TDD RED→GREEN: missing pure function, then missing MCP tool, followed by adversarial boundary RED cases; never count infrastructure failures as behavioral RED.
- Real **built** Node24 STDIO and loopback HTTP tools/list and call, including exact registered inventory and full HTTP SSE byte count on a large valid corpus. Assert structured/text fidelity, 96 KiB pure overflow and 256 KiB result/wire limits; no private-state access, no new provider call or regression to M10.0.
- Independent source/provenance and MCP/transport reviews with zero unresolved Critical/Important findings, full Node24 test + format/lint/typecheck/build/diff gates, exact final PR-head CI and post-merge `main` CI before moving this scoped subrequirement to `VERIFIED`. **M10 broader competitor analysis, live discovery, trends and source verification remain unfinished** even then.

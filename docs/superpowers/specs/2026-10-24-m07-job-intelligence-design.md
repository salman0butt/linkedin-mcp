# M07 Job Intelligence — Design

Date: 2026-10-24. Requirement: `R-M07-JOBINTEL`. Milestone: `docs/milestones/M07-job-intelligence.md`.

## Intent and use

Let an MCP client analyze one or several M06 normalized job records and help a person decide which opportunities deserve attention. Extract explicit requirements, identify documented work-location and visa sponsorship signals, explain matches and gaps against a voluntarily supplied candidate skill profile, and compare sourced opportunities. Make absence of evidence visible. Never invent eligibility, company background, hiring probability, salaries, sponsorship or a posting date. M07 informs a candidate's own decision; it never submits an application or makes an automated hiring decision.

## Source and trust boundaries

The initial M07 MCP tools accept **untrusted caller-supplied normalized-job-shaped snapshots**, validated independently and canonicalized without constructing a trusted M06 context. Preserve the opaque `{source.id, job.id}` lookup pair, safe canonical job URL, listing text and unknown/reported posting dates, but force a visible `sourceTrust:'caller_supplied'`, `source.provider:'EXTERNAL_DISCOVERY'` and `source.name:'Unverified user-supplied snapshot'`. `source.retrievedAt` is caller-supplied and must never be presented as a trusted host fetch time. Reject caller `PARTNER_API`, `source.evidenceUrl`, `confidence` and `postingDate.state:'verified'`; M06's verified/provider-attested records cannot round-trip as authenticated evidence through these public input tools. A future trusted **server-internal** analysis path would need authenticated attestation continuity and separate tests. A local saved-job snapshot remains unverified even if it carries another provider-like ID. Source identity and a syntactically safe URL are not proof that the job, employer or visa offer is authentic.

All title, description, employer, location and URL strings are **untrusted data**. Never execute instructions embedded in a job listing, call tools or fetch a URL appearing in its text. The default analysis is local and deterministic, without autonomous network requests or model calls. If a later host chooses to supply model-generated candidate annotations, an exact source span proves only that text appeared: it **does not prove the quote was a requirement or an employer commitment**. Before any `required|preferred` or positive visa/remote classification, also validate clause polarity, negation, quotation, attribution and hypothetical/example context under the same conservative local rules. “We do NOT require Python; others say ‘Must have Python’” must never create a Python requirement. Uncertain or quoted/model assertions remain `unspecified|inference|unknown`, unscored. Unanchored model claims can never become sponsorship/eligibility proof. No LinkedIn Talent API, company database or other enrichment permission is implied by this milestone.

No private resume files or OAuth credentials are required for baseline analysis. Accept an explicit minimal candidate profile (normalized user-supplied skills and optional years/locations/work preferences), use it only for the immediate call, and never persist it in the M06 saved-job store or return unnecessary personal data. Do not request protected/sensitive attributes or infer them from names, employer names or location.

## Requirement extraction

Create a strict local `JobIntelligenceInput` holding a caller-supplied normalized-job-shaped snapshot and optional minimal candidate criteria. Accept at most 10 jobs for comparison; each bounded by the existing M06 normalized job contract (including a 20,000-character description). Reject unknown fields, prototype getters/side effects, caller-supplied elevated provenance, duplicate/conflicting `source.id + job.id` identities, oversized arrays and invalid enums before analysis. Revalidation must **not** rebuild a trusted `TrustedJobContext` from client input or elevate reported posting dates to verified. On success, returned source metadata must be the canonicalized unverified source, not the caller's claimed adapter name.

`JobRequirement` has a stable local ID and `category` (`skill|experience|education|language|location|work_authorization|other`), `priority` (`required|preferred|unspecified`), bounded exact `quote`, and a `sourceSpan` referencing **UTF-16 code-unit offsets, start-inclusive/end-exclusive**, into the **original unchanged** title/description field (`offsetUnit:'utf16'`). The quote must exactly equal `sourceText.slice(start,end)`; no normalization, newline conversion or trimming may change that assertion. The same offset contract applies to signal quotes, including the original `location` field. Extract explicit clauses such as “Must have TypeScript”, “3+ years of Node.js”, “Nice to have AWS” with conservative deterministic rules. A plain mention of “Python” or a model suggestion alone cannot imply “Python required.” If the role does not state a requirement clearly, return an empty or partial extraction with an explanation, never synthetic candidate requirements. Cap the returned requirement set (maximum 50), mark truncation explicitly and preserve deterministic source order.

## Relocation, work authorization and company signals

`JobLocationSignals` keeps distinct `workplace` as supplied by the job, `remoteEligibility` (`explicit_yes|explicit_no|unknown|conflicting`) and `sponsorship` (`explicit_yes|explicit_no|unknown|conflicting`). Every non-unknown sponsorship or remote-eligibility classification includes one or more exact evidence spans from **title, description or original location** (`field`, `start`, `end`, `offsetUnit:'utf16'`), with any stated country/jurisdiction attached as explicit scoped text. Reconcile restrictive qualifiers across all these fields: “work from anywhere” in the description and “US only” in `location` is `conflicting` for worldwide remote eligibility, never unqualified `explicit_yes`; “visas sponsored” alongside “must already have US work authorization” is `conflicting` unless a supported jurisdiction/condition resolves it. “Remote” workplace alone does not mean “work from any country”; a visa or relocation **mention** alone does not prove actual sponsorship. An explicit negation (“no visa sponsorship”, “must already have authorization”) must not be reversed by substring matching; conflicting positive and negative claims become `conflicting` with both citations. Separate `relocationAssistance` from `visaSponsorship`; state jurisdiction only when explicit. Country citizenship, candidate legal eligibility and real-time immigration rules remain unknown absent independent host verification.

Company context is restricted to the listing's `companyName`, source identity, canonical URL and quoted claims about the employer; no guessed company size, headquarters, funding, recruiter authenticity or working culture. A future enrichment provider would need a separate host-configured entitlement, evidence and validation contract.

## Candidate fit and comparison

Input profile: `{skills:string[]; yearsOfExperience?:number; preferredWorkplace?:'remote'|'hybrid'|'on_site'; preferredLocations?:string[]}`. Limit skills to 80 unique 1–80-character strings and locations to 20 unique 1–120-character strings; years are integer 0–80. Treat every field as a caller statement. Skill comparison uses normalized exact/controlled aliases (not freeform semantic guessing) and yields matched, missing and unknown requirement sets with each source quote. Do not infer skills from a name, employer or portfolio URL. Experience claims in an unstructured line cannot automatically be compared to years unless an explicit, bounded number is extracted.

Fit result uses `evaluated|insufficient_evidence`; an `evaluated` result may carry a descriptive, reproducible priority/coverage breakdown and a bounded **advisory** score, computed solely from sourced required/preferred criteria and explicit caller skills. The fit evaluator must consume the **whole extraction result** including `truncated` and evidence status, not only the first 50 requirements. If extraction truncated or the evidence status is incomplete in a way that hides candidate requirements, return `insufficient_evidence` and no numeric score; a 51st omitted required skill cannot yield false 100% fit. Unspecified, unparseable and unverified criteria remain unknown rather than scored as failure. To avoid false completeness, M07 v1 issues an advisory score **only when every explicitly classified required/preferred requirement is a recognized `skill` with exact supported alias matching**; experience, education, language, authorization, location and `other` requirements remain in the qualitative evidence report and make the numeric score unavailable. With no extractable requirements or no candidate skills, likewise return no numerical score; a score is never a hiring probability. Exact scoring weights and allowed aliases are fixed in the implementation plan and checked with golden fixtures.

`compareJobs` accepts 2–10 source-scoped distinct caller snapshots and an optional same transient profile. Results are stable in input order with identical independent analysis rules, missing-evidence flags and side-by-side sourced differences. Any item with truncated/incomplete extraction has `insufficient_evidence` rather than an overconfident score; comparison cannot rank a truncated item by that score. Cross-source duplicate titles are not silently merged; two distinct records with the same source-scoped identity require conflict rejection or exact evidence-equivalence proof. Do not compare monetary salaries across currencies or time periods or rank sponsorship without explicit evidence.

## MCP and transport

Expose strictly read-only local MCP tools `linkedin.jobs.analyze` and `linkedin.jobs.compare` in the shared stdio/HTTP runtime. Their capability IDs are `jobs.analyze` and `jobs.compare`, each `LOCAL_ONLY` and advertised as available after the implementation is verified in either STDIO or HTTP even without a search provider; the former placeholder `jobs.score` is replaced, with no undocumented alias. Analyze only provided **canonicalized unverified** snapshots in M07 v1; a host-bound `JobRef` service path is reserved for a later separate iteration with an authenticated continuity contract. An explicit `sourceTrust:'caller_supplied'` remains visible in MCP results and all display source fields are neutralized as above. Result envelopes follow the existing service taxonomy and error sanitizer, contain no private profile fields and have bounded serialized response size. HTTP must not be allowed to read the local saved-job store via analysis arguments or internal fallback. Saved jobs and searches stay unchanged. Both tools operate without a configured external jobs provider when explicit safe snapshots are supplied.

## Engineering, validation and review

Use Node 24, TypeScript, existing Zod/MCP runtime and Vitest. Follow M06's pure core data contracts and existing MCP error shapes. Implement in M07.1–M07.6 increments with observed failing tests before code; independent security review at M07.7. Test hostile prompt text, fabricated partner/date metadata, contradictory sponsorship assertions, ambiguous employment eligibility, missing descriptions and empty candidate profiles, Unicode/source-offset fidelity, long texts, duplicates, prototype pollution and output limits. Real STDIO/HTTP contract smoke tests must prove no extra network or private-store effects. All post-merge evidence is exact-SHA CI, with unresolved Critical/Important findings at zero.

## Owner-authorized implementation decisions

The PRD and standing `AGENTS.md` authorize autonomous milestone design and implementation. Prefer conservative source-anchored analysis to unverifiable AI enrichment. Keep actual work authorization, employer verification and application submission outside M07. If a feature cannot be responsibly supported from listing text, expose `unknown` or `insufficient_evidence` rather than a positive claim.

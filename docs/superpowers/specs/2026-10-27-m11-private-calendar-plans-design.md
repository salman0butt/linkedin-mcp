# M11.1 — Opt-in private local content calendar plans

## Context, alternatives, decision

M11.0 is VERIFIED/MERGED at main `96e4052eb4fd92d24afb0489c3142e65447e63c7` (PR #21, feature CI `40472594047` and exact merged-main push CI `40475275490` SUCCESS). Its `linkedin.calendar.preview` is stateless and cannot persist, authorize, queue or execute anything. M11 requires substantially more work before actual scheduled publishing. Compare (a) a real scheduler now (unsafe without future-time approval/claim/provider model), (b) an always-on HTTP calendar database (violates private-store transport posture), (c) **explicit host-opted-in local STDIO-only calendar plan CRUD**. Choose (c): useful durable drafts with no execution or provider dependency.

## Contract and safety

- Host opts in with `LINKEDIN_MCP_CALENDAR_STORE_PATH`, a canonical absolute nonoverlapping local file path; without configuration or over HTTP, saved operations return fixed `unsupported/local_store_not_available` even when a private runtime/store was injected into an HTTP server. No MCP input can configure filesystem paths. Separate from job/article, auth, publishing ledger and media roots and companion files.
- `LocalCalendarPlanStore` exposes `create({idempotencyKey,calendar})`, `update({id,expectedRevision,calendar})`, `get({id})`, `list()`, `remove({id,expectedRevision})`. Plan contains UUID `id`, monotonic positive `revision`, canonical ISO `createdAt`/`updatedAt`, and exact validated caller definition `calendar:{referenceUtc,items}`. List returns only `id,revision,createdAt,updatedAt,referenceUtc,itemCount`; no complete labels.
- Every `calendar` input goes through M11.0 `previewLocalContentCalendar` strict own-data and canonical UTC parser first; then deep-copy data without normalization, preserving label Unicode/spacing and original item order. No post payload, media path, approval receipt, OAuth secret, job execution status or queue metadata is accepted or persisted. Reference date is caller-declared; do not silently replace with wall clock or future-time reauthorization.
- `idempotencyKey`: raw ASCII `[A-Za-z0-9][A-Za-z0-9._:-]{3,127}`; create replays identical payload to the same live plan, conflicting value fails `idempotency_conflict`; history/tombstones prevent resurrecting a deleted plan. Update/remove require exact expected revision (`revision_conflict` on stale write); UUID identities are host-generated. No side effects from get/list except local filesystem checks/locking.
- Max **20 active plans**, **2,048 create key history** and **2 MiB persisted state**. Invalid input, not found, revision conflict, idempotency conflict, capacity, unsafe/corrupt store and uncertain committed outcome have stable sanitized fixed-code responses. Fail closed rather than silently resetting damaged state. No path, labels, unknown secret fields or error stack in MCP errors.
- Based on M08 private article store safety: owner-private file `0600`, private parent `0700`, regular single-link files only, no symlinks, O_NOFOLLOW, pinned parent directories, `O_EXCL` lock bounded wait, exclusive staged temporary file, sync+rename+directory sync, re-read integrity, `.initialized` sentinel, corruption/invalid UTF8/orphan temporary/lock detectable and never automatically discarded. Path-based operations do not claim atomic `openat` protection against a malicious same-UID process. Remain bounded under restart, separate processes and crash/ambiguous completion.
- MCP methods `linkedin.calendar.plans.create|update|get|list|remove`, strict typed schemas, fixed local provenance, dual text/structured parity and ≤256 KiB raw JSON-RPC/SSE transport. Default tool listings may expose these methods but HTTP must never reach a private store. Capability `calendar.plans` **LOCAL_ONLY / UNAVAILABLE by default / ACTIVE** with explicit STDIO opt-in access note; `calendar.preview` remains AVAILABLE. `schedule.create` **PLANNED/UNAVAILABLE**.
- Every stored-plan response must explicitly say `execution:not_queued`, `approval:not_evaluated`, `publication:not_attempted`; `persistence:private_local` when stored, never imply LinkedIn scheduling, provider-auth or source verification. No future timer/cron/queue, write approval or network/provider call.

## Acceptance and review focus

1. Genuine RED before store code: missing module or expected nonexistent method; then GREEN with exact original Unicode/label/order across restart, create replay/conflict, CAS update/remove and tombstone behavior.
2. Independent child-process writes serialize; malicious symlink/hardlink/non-private directory/corrupted JSON/invalid UTF8/leftover lock/sentinel/temporary fails closed without modifying prior committed data.
3. Root/calendar/items invalid proxies, getters (zero invocations), symbols, extra secret keys, dense-array holes, casefold duplicate IDs, dates past 90d, invalid timestamps or unsafe labels fail before any disk modification.
4. Real SDK pre-handler Zod errors redact arbitrary secret key names/values, HTTP private-store injection never reads the store (including getter traps), unknown request IDs are bounded, complete raw SSE stays ≤256 KiB.
5. List only minimal metadata, 20-plan and 2 MiB ceiling, 2,048-key budget; no leaking private plans via HTTP or cross-store path collisions.
